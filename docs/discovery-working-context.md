# The Damda Discovery — 작업 기준

마지막 갱신: 2026-09-29. 이 문서는 대화 전체의 복원본이 아니다. 사용자 확인 사항, 공유된 마지막 대화 화면, `discovery-v0.1` 코드에서 확인한 사실을 구분해 적는다.

## 사업 목적 (사용자 확인)

Discovery는 주식회사 더담다가 **고객에게 SEO·AEO·GEO 서비스를 제공하기 위한 내부 운영 시스템**이다. 더담다 홈페이지는 첫 적용·검증 사례다. 서비스는 검색이나 AI의 노출을 보장하는 상품으로 표현하지 않는다. 상담, 현황 확인, 실행, 측정 및 결과 설명을 고객 프로젝트별로 운영한다. '무료 사용자에게 배포할 앱'은 이 프로젝트의 목표를 설명하는 표현이 아니다.

## 운영 흐름

1. 상담 접수 → 고객 업체 정보와 홈페이지 현황 진단 → 사람이 진단서 확인·전달.
2. 상담 정보 및 실제 홈페이지 근거를 AI Source Profile의 질문 재료로 정리. WHO / FOR_WHOM / WHERE / WHEN / SERVICE / PURPOSE / PROBLEM / CONDITION / PREFERENCE / URGENCY / ACTION으로 구분한다. SEO/GEO 개선 권고를 고객의 실제 목적·문제로 섞지 않는다.
3. 실제 잠재고객이 물을 법한 기본·상황·롱테일 질문 후보를 만든다. 사람이 반복 측정할 Benchmark 질문을 선정한다. 측정 전의 임시 자동 Benchmark 정리 규칙을 유지한다.
4. 같은 Benchmark를 검색과 AI 채널에서 Day 0 측정한다. 채널은 Core AI / Search / Extended AI로 구분한다. 채널 간 결과 차이는 오류로 단정하지 않고 출처와 일시를 함께 기록한다.
5. 측정 근거로 분석과 개선 초안을 만든다. 담당자가 승인·수정·보류하고 작업한다. 승인 없이 홈페이지 변경이나 고객 전송을 자동으로 하지 않는다.
6. 같은 질문으로 재측정하고 변화 및 한계를 기록한다. 프로젝트의 Observed(관찰) / Interpreted(해석) / Outcome(이후 결과)을 연결해 보고한다.

## 구조와 현재 구현

- `/discovery`: 회사 전체의 상담 및 프로젝트 운영 대시보드.
- `/discovery/projects/{id}`: 업체별 내부 대시보드. 질문, 측정, 분석, 작업, 캘린더를 연결한다.
- `/discovery/projects/{id}/questions`: 질문 재료 추출, 후보 생성, Benchmark 선정.
- `/discovery/archive`와 `/discovery/archive/projects/{id}`: 사전 진단과 프로젝트별 분석·후속 기록.
- 고객에게 보여주는 화면은 내부 운영 화면과 별개로 설계한다. 현재 `/client/demo`는 미리보기다.
- `supabase/discovery_analysis_history.sql`: 분석 이력 저장용 테이블. 사용자는 SQL 실행 성공을 알렸다.

## 확인된 상태와 제한

- 작업 브랜치: `discovery-v0.1`. 시작 시 원격 HEAD는 `a9d3511`이었다. 이 세션의 수정은 로컬 작업 트리에 있으며 푸시·배포하지 않았다.
- TypeScript 검사와 Next.js 프로덕션 빌드는 통과했다. 이는 외부 API 및 실제 DB 연동 검증을 뜻하지 않는다.
- 사용자가 알려준 Preview `https://discovery-preview.the-damda.co.kr/discovery`는 이 환경에서 접속되지 않았다. 현재 배포 화면을 확인했다고 주장하지 않는다.
- SQL 실행 성공 이후에도 분석 저장·조회, 질문 추출, 채널 측정, 승인 흐름은 실제 데이터로 끝까지 확인해야 한다.
- 기존 대화의 상세한 '5가지' 원문은 이 세션에서 확인되지 않았다. 공유된 마지막 화면의 작업 목록을 근거로 복원한 코드이며, 그 목록과 구현의 완전한 일치는 아직 검증되지 않았다.

## 이어서 확인할 일

1. 사용자 로그인 상태에서 AI Source Profile 생성 → 재료와 근거 확인 → 질문 후보 생성 → Benchmark 저장.
2. 서로 다른 프로젝트에서 수동·OpenAI·Gemini 측정이 올바른 프로젝트에 저장되는지 확인.
3. Day 0 분석 생성 → `discovery_analysis_history` 저장 및 재조회 → 아카이브의 후속 측정·작업 표시 확인.
4. 사업 서비스 흐름에 맞춰 고객용 보고 화면, 승인·전달 단계, 실제 측정 지표를 점검.

이 문서에서 사용자 확인 사항과 추정 사항이 충돌하면 사용자 설명을 기준으로 고친다.
