# Discovery V2 — 엔진 역할과 변경 경계

## 기준

같은 모델을 사용하더라도 책임과 입력·출력을 분리한다. 측정 답변은 외부 관찰 원본이며 해석이나 작업 기록으로 덮어쓰지 않는다. 고객 공개·홈페이지 수정·결제는 엔진 초안 생성과 별도 승인이다.

| 역할 | 현재 코드 | 입력 → 출력 | 변경 영향 |
|---|---|---|---|
| 정보 구성 | engagementStore, channelAssets, ontology, 홈페이지 진단 | 고객 사실·목표·채널 → 검토 자료 | 관련 질문·판단 재검토 |
| 질문·여정 | questionContext, questionReview, generate-questions | 검토 자료 → 질문 후보·직원 선정 | 해당 질문의 이후 비교 검토 |
| 측정 | measure-* 라우트, discovery/evidence | 질문·채널 → 원본 답변·출처·조건 | 새 측정은 기존 측정을 삭제하지 않음 |
| 검토 | analyze-day0, analyze-naver, workPlan | 원본 근거 → 해석·작업 판단 | 실제 답변·적용 기록 유지 |
| 개선 구성 | discovery/improvementPlanning, discovery/executionComposition | 해석·승인 과제 → 수정안·견적 후보 | 작업 정의 변경 시 해당 초안·판단·견적 후보만 무효화 |
| 성과·보고 | discovery/performanceReporting, caseReport | 적용·재측정 → 비교·보고서 초안 | 공개본은 별도 확정 |

## 이번 분리

- 원본 추출·측정 참조·워크플로우 첨부를 evidence 모듈로 통합했다. 전달 자료는 복사하여 하위 모듈 변경이 원본 메모리까지 전파되지 않게 한다.
- 개선안 파싱과 실행 프롬프트 구성을 독립 모듈로 옮겼다. 실행 프롬프트 모듈에는 DB·네트워크·공개 권한이 없다.
- 성과 비교와 보고 텍스트 구성을 독립 모듈로 옮겼다.
- 기존 improvementWorkflow import는 호환 진입점으로 유지하여 호출부를 한꺼번에 교체하지 않는다.
- 저장 형식·테이블·공개 승인 절차는 그대로 유지한다. SQL 불필요.

## 아직 하지 않은 것

여섯 독립 서비스, 전체 파이프라인 자동 무효화, 단계별 작업 큐·자동 재시도, 다중 대화 구매 여정 저장, 실제 소비자 AI 화면 자동 수집은 아직 구현하지 않았다. 기존 기능을 각 역할에 배치한 뒤 영향 범위를 검증하면서 순차적으로 분리한다. 엔진이라는 이름만 붙여 완성으로 판단하지 않는다.

## 다음 순서

1. 고객 목표·사실·질문 버전 간 연결 기준 확정. 데이터 구조 변경 전 기존 기록 호환 확인.
2. 질문·여정 및 검토 요청의 입출력을 분리. 원본 답변 보존 테스트 유지.
3. 변경 영향 표시와 해당 단계만 재실행하는 작업 큐.
4. 제품 추천·판매처 연결의 별도 판정과 실제 화면 수집 검증.

## 2차 연결 구현

- Day 0·비교 및 관리 프로젝트 네이버 분석에 analysis-context 메타데이터를 추가한다. 업체·목표·확인 사실·벤치마크·등록 채널·저장 홈페이지·질문 재료·개념 관계를 항목별 해시로 비교한다. 실제 홈페이지의 실시간 변경 감지는 별도 기능이다.
- 작업 화면에서 현재 관리 기준과 분석 당시 기준이 달라진 항목을 표시한다. 과거 메타데이터가 없으면 unknown이며 일치로 취급하지 않는다. 프로젝트 전체를 초기화하거나 원본 기록을 삭제하지 않는다.
- 초안 생성·저장 사이 입력 변경을 확인하고, 초안 저장 후 입력이 달라지면 적용 완료 전 재검토·초안 갱신을 요청한다. 예전 초안은 기준 메타데이터가 없어 자동 차단하지 않는 호환 정책이다.
- 리뷰 프롬프트는 reviewComposition 모듈로 분리했다. DB 읽기·인증은 라우트, 지시문 구성은 독립 함수가 담당한다.
- 네이버 프로젝트 검토에 고객 목표·직원 확인 사실을 전달한다. 상담 전 진단은 기존 제한 범위를 유지한다.
- 워크플로우 저장은 분석 기준 메타데이터를 보존하며 측정 근거 추출에는 포함하지 않는다.
- 입력 기준은 경고·재검토용이며 원본 측정의 정확성·실제 노출·성과를 보증하지 않는다. 개별 질문별 의존성 추적 및 자동 재실행 큐는 후속 작업이다.
- 추가 테이블·SQL은 필요 없다. 모든 저장은 기존 JSON 구조와 호환한다.

## 3차 연결 구현

- 새 분석 기준에는 벤치마크 질문별 해시가 포함된다. 추가·수정·해제된 질문 ID를 구분한다. 이전 해시가 없는 자료는 개별 변경을 추정하지 않는다.
- reexecute는 직원이 선택한 원본 분석 하나의 재실행을 담당한다. 실행·완료·실패·시도 횟수를 기존 분석 JSON의 engine-runs 메타데이터로 저장한다.
- 같은 원본·입력 기준의 실행 중 작업은 중복 호출하지 않고, 완료 작업은 결과를 재사용한다. 실패 재시도는 명시적으로 요청하며 동일 기준 최대 3회다.
- AI 분석은 저장된 측정을 다시 분석한다. 질문 변경은 기존 답변을 새 질문 결과로 해석하지 않고 새 측정을 요청한다. 네이버는 원래 API 검색 채널·트렌드·쇼핑 카테고리를 재조회한다. 실제 AI 소비자 화면 수집은 포함하지 않는다.
- 새 분석은 원본을 덮어쓰지 않고 새 이력으로 저장하며 개선 과제를 연결한다. 연결 실패는 분석 저장 완료와 구별해 안내한다.
- 예약 실행 및 무인 워커는 아직 없다. 버튼으로 시작한 요청 안에서 실행한다. 실행 중 프로세스가 종료되면 임의 재호출하지 않고 확인 대상으로 남긴다.
- 개별 과제와 질문의 완전한 의존성 그래프, 대화 구매 여정 및 실제 소비자 AI 브라우저 자동 수집은 별도 작업이다.
